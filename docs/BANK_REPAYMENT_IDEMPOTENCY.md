# Идемпотентность погашения банковских кредитов

## Цель

Повторная обработка одного пользовательского намерения погасить кредит не должна повторно списывать деньги, повторно начислять сумму в банковский пул или повторно возвращать залог.

## Ключ запроса

Пользовательская точка входа создаёт случайный request token при открытии деталей кредита. Токен сохраняется в GUI-holder и передаётся в операцию погашения:

- для полного погашения — непосредственно из обработчика GUI;
- для частичного погашения — вместе с ожидаемым вводом суммы в chat-field.

Сервис формирует SQLite operation ID с префиксом `bank:loan:repay:` и стабильный fingerprint из версии схемы запроса, UUID заёмщика, ID кредита и точного значения запрошенной суммы (`Double.toHexString`).

Тот же токен и те же параметры означают повтор исходного намерения. Тот же токен с другим игроком, кредитом или суммой отклоняется как конфликт fingerprint.

## Транзакция

Проверка уже подтверждённого operation ID выполняется до проверки актуального статуса кредита и до подготовки нового snapshot. Это важно для повтора после успешного коммита: кредит уже может иметь статус REPAID, но повтор должен вернуть успешный результат, а не пытаться списать деньги снова.

При первой обработке wallet delta, банковский snapshot, возврат залога и финансовый журнал фиксируются единым SQLite-коммитом через `applyBatchOnce`.

Для пользовательских операций используется fingerprint намерения, а не fingerprint текущего snapshot. Время начисления, временные метки и состояние других банковских сущностей могут измениться между первой попыткой и повтором; они не должны превращать тот же request token в конфликт.

## Границы гарантии

- Один и тот же request token защищает повторную доставку одного действия, если вызывающая сторона повторно использует этот token.
- GUI сохраняет token на время одного экрана деталей кредита и передаёт его через ввод суммы.
- Повторное открытие экрана создаёт новое намерение и новый token. Это сознательно позволяет игроку совершить следующий самостоятельный платёж, в том числе на ту же сумму.
- Совместимый метод сервиса без request token создаёт новый случайный token. Пользовательские точки входа должны использовать перегрузку с явным token.
- Это не дедупликация двух независимых кликов, сделанных после повторного открытия GUI. Для такой гарантии понадобился бы долговечный пользовательский платёжный intent с отдельным жизненным циклом и явным подтверждением/отменой.

## Тестирование

SQLite-тест проверяет, что повтор одного request token с тем же fingerprint не меняет повторно баланс, банковский snapshot и число записей журнала, даже если повторный вызов принёс другой snapshot. Повторное использование ключа с другим fingerprint должно завершаться ошибкой.
