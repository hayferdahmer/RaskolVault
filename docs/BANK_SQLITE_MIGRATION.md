# Миграция банковского хранилища в SQLite

## Что переносится

Рабочее хранилище банка перенесено из пяти YAML-файлов в отдельные таблицы общего SQLite-леджера:

- `bank_accounts` — вклады, начисленные проценты, срок и статус;
- `bank_loans` — кредиты, погашения, начисления, залог и статус;
- `bank_pools` — пулы вкладов и процентные резервы по нации и валюте;
- `bank_credit` — счётчики погашенных и дефолтных кредитов;
- `bank_pending_returns` — предметы залога, ожидающие возврата игроку;
- `bank_storage_meta` — маркер завершённого импорта.

## Первый запуск после обновления

1. SQLite создаёт таблицы банковского хранилища.
2. Если маркер `yaml_import_v1` отсутствует, плагин читает прежние YAML-файлы.
3. Данные записываются в SQLite отдельными транзакциями для каждого набора таблиц.
4. Маркер импорта устанавливается только после успешного сохранения всех наборов.
5. Исходные YAML-файлы не удаляются и остаются резервной копией.

Если сохранение любого набора завершается ошибкой, маркер не устанавливается. При следующем запуске импорт повторяется из исходных YAML-файлов. Это делает процедуру повторяемой после частичного сбоя.

## Контроль после миграции

Проверять нужно не только факт запуска:

- число счетов и кредитов;
- сумму активных вкладов по валюте и нации;
- суммы основного пула и процентного резерва;
- остатки начисленных процентов;
- статусы погашенных и ликвидированных кредитов;
- число отложенных возвратов предметов.

До отдельного подтверждения корректности данных YAML-файлы не удалять.

## Важное ограничение текущего этапа

Персистентность банковских сущностей уже находится в SQLite, но некоторые бизнес-операции пока выполняют несколько отдельных коммитов: например, списание кошелька и обновление пула/счёта. Следующий этап должен объединить изменение кошелька, банковских сущностей и финансового журнала в одну идемпотентную SQLite-транзакцию. До завершения этого этапа миграция хранилища сама по себе не означает полной транзакционной готовности банка.
